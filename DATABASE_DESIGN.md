# Database Design

## Infinity Blog

**Version:** 1.0  
**Database:** MySQL

---

## 1. Design goals

- Maintain authors, administrators, categories, posts, summaries, and audit history consistently.
- Enforce relationships with primary and foreign keys.
- Prevent unauthorized code paths from being disguised as data integrity rules.
- Keep secrets out of database schema and API responses.

## 2. Logical entity relationship

```text
users (1) ----------------< posts >---------------- (1) categories
   |                         |
   |                         +-- summary metadata
   |
   +----------------------< audit_logs (actor)

login_rate_limits (independent HMAC-keyed buckets)
```

A user can author many posts. A category can contain many posts. A post references one author and, where assigned, one category. Audit events may retain a nullable actor reference so records survive account deactivation/deletion according to the retention policy.

## 3. `users`

| Column | Type (suggested) | Rules / purpose |
|---|---|---|
| `id` | BIGINT UNSIGNED | Primary key, auto-increment |
| `username` | VARCHAR(190) | Required, unique; supports the two configured administrator identifiers |
| `display_name` | VARCHAR(190) | Required display label |
| `email` | VARCHAR(254) NULL | Optional/unique if collected |
| `password_hash` | VARCHAR(255) | Required; output never exposed |
| `auth_version` | BIGINT UNSIGNED | Required, default 1; incremented atomically when credentials are rotated/reset to revoke prior sessions |
| `role` | VARCHAR(20) or ENUM | Allowlist: `admin`, `author` |
| `status` | VARCHAR(20) or ENUM | Allowlist: `active`, `inactive` |
| `must_change_password` | TINYINT(1) | Set where setup policy requires a first-login change |
| `created_at` | DATETIME | Creation timestamp |
| `updated_at` | DATETIME | Last update timestamp |
| `last_login_at` | DATETIME NULL | Optional operational metadata |

Constraints: unique normalized username; unique email if email is collected; valid role/status values. Store only a secure password hash, not the password itself.

The additive migration `202610090003_add_auth_version_to_users` adds `auth_version` without rewriting the initial schema migration. A successful login copies the current database value into the server-side session. The reusable `AuthGuard` compares it with the current user row on every protected request and clears the session when it is missing or stale. Credential-changing code must update the password hash and increment this value in the same database statement. The version is never accepted from request parameters or returned to clients. This performs one indexed user lookup per guard check and does not depend on PHP session-store enumeration. Rollback removes the column and its revocation state, so it requires the migration runner's explicit destructive confirmation and a coordinated deployment/session invalidation plan.

## 4. `categories`

| Column | Type (suggested) | Rules / purpose |
|---|---|---|
| `id` | BIGINT UNSIGNED | Primary key |
| `name` | VARCHAR(120) | Required; normalized unique policy |
| `slug` | VARCHAR(140) | Required, unique URL-safe value generated by the server from `name` |
| `description` | VARCHAR(500) NULL | Optional description |
| `is_active` | TINYINT(1) | Active categories may be newly assigned |
| `created_by` | BIGINT UNSIGNED | FK to users, admin creator |
| `created_at` | DATETIME | Creation timestamp |
| `updated_at` | DATETIME | Update timestamp |

Rules: only admin endpoints may mutate categories. Clients do not choose category slugs. Generate a lowercase URL-safe base from the normalized name; append a deterministic numeric suffix when the base is already used, and retry a concurrent collision while preserving the unique database constraint. Duplicate normalized names are rejected. Deactivate instead of hard-delete when posts reference a category.

## 5. `posts`

| Column | Type (suggested) | Rules / purpose |
|---|---|---|
| `id` | BIGINT UNSIGNED | Primary key |
| `author_id` | BIGINT UNSIGNED | Required FK to `users.id` |
| `category_id` | BIGINT UNSIGNED NULL | FK to `categories.id`; draft may be uncategorized if supported |
| `title` | VARCHAR(255) | Required, length-limited |
| `content` | MEDIUMTEXT or TEXT | Required body, size-limited at application layer |
| `summary` | TEXT NULL | Plain-text AI summary only |
| `summary_status` | VARCHAR(20) or ENUM | `none`, `ready`, `stale`, `failed` (a temporary `generating` state may be used if needed) |
| `summary_source_hash` | CHAR(64) NULL | Hash of title/body used for current summary |
| `summary_generated_at` | DATETIME NULL | Last successful generation time |
| `status` | VARCHAR(20) or ENUM | `draft`, `published` |
| `published_at` | DATETIME NULL | Publication timestamp, if published |
| `created_at` | DATETIME | Creation timestamp |
| `updated_at` | DATETIME | Last modification timestamp |

Rules:

- `author_id` comes from the authenticated session, never from client authority.
- Publish requires required fields and an active category.
- Public queries filter `status = 'published'` at database/query level.
- Title/body changes mark an existing summary stale.
- Public views should not show a stale summary as if current.
- Use appropriate indexes, including `(status, published_at)`, `author_id`, `category_id`, and combinations proven by query patterns.
- Dashboard counts are derived with aggregate queries over `posts`: author counts filter by the authenticated `author_id`, while admin counts span all posts. The current `draft` and `published` statuses define the count buckets. No view-count field/table is part of Version 1.0.

## 6. `audit_logs`

| Column | Type (suggested) | Rules / purpose |
|---|---|---|
| `id` | BIGINT UNSIGNED | Primary key |
| `actor_user_id` | BIGINT UNSIGNED NULL | FK to users, nullable for system events |
| `action` | VARCHAR(80) | Allowlisted action name |
| `entity_type` | VARCHAR(50) | e.g. `post`, `category`, `user`, `auth` |
| `entity_id` | BIGINT UNSIGNED NULL | Reference ID; may be retained even if entity is deleted |
| `metadata` | JSON NULL | Safe, minimal metadata only |
| `created_at` | DATETIME | Event timestamp |

Never log passwords, session cookies, API keys, full article content, or complete provider requests/responses. Define retention and access policy before production use.

## 7. `login_rate_limits`

Implemented by additive migration `202610090002_create_login_rate_limits`. It stores only login limiter state; no raw username or IP address is persisted.

| Column | Type | Rules / purpose |
|---|---|---|
| `bucket_hash` | CHAR(64) ASCII binary | Primary key; HMAC-SHA-256 of bucket type and normalized identifier or source address, keyed by required `APP_KEY` |
| `bucket_type` | VARCHAR(16) | Check constraint: `identifier`, `source`, or `global` |
| `failed_attempts` | INT UNSIGNED | Positive failed-login count in the fixed window |
| `window_started_at` | DATETIME | First failed attempt in the current window (UTC) |
| `expires_at` | DATETIME | End of the 15-minute fixed window; indexed for pruning |
| `updated_at` | DATETIME | Last atomic increment time (UTC) |

The MySQL implementation allows 5 failures per normalized identifier and 20 failures per socket source address in 15 minutes, with a global cap of 100,000 failures per 15 minutes. The global cap bounds the rate at which new HMAC buckets can accumulate and fails closed with `429` until expiry. It ignores proxy forwarding headers. MySQL upserts increment counters atomically; concurrent requests that pass a check before recording may exceed a threshold by the size of that in-flight batch. Expired buckets are pruned during login checks and before inserts. Key rotation makes old hashes unreachable; expired rows are pruned normally. The runtime account needs `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on this table. Summary rate limiting remains a later feature and does not use this login table.

## 8. Foreign-key behavior

- Posts reference users; user deactivation is safer than deleting a user with posts.
- Posts reference categories; use restrictive delete behavior and prefer category deactivation.
- Audit actors can become null if an account is removed, preserving event history according to policy.
- Do not cascade-delete posts simply because a category is deleted.

## 9. Migration and backup rules

- Use versioned migration/schema files.
- Apply schema changes in a controlled order.
- Back up before production migrations.
- Test schema creation from an empty database.
- Do not include real data or production secrets in sample dumps.
- Test restoring backups, not just creating them.

### Phase 1 implementation decisions

- The first migration is `202610090001_create_cms_schema`; `bin/migrate.php` records applied migration IDs in `schema_migrations` and can safely re-run the initial `CREATE TABLE IF NOT EXISTS` migration.
- Tables use InnoDB, `utf8mb4`, and `utf8mb4_unicode_ci`. Usernames, category names, and slugs therefore have case-insensitive and accent-insensitive uniqueness at the database layer. Application validation should normalize category slugs to lowercase URL-safe values before persistence.
- Role, account status, post status, and summary status are allowlisted with enforced `CHECK` constraints. The supported MySQL baseline is 8.0.16 or newer so these checks are enforced.
- The migration runner checks the connected server version before applying schema changes and rejects versions older than MySQL 8.0.16.
- Category deactivation changes only `is_active`; it preserves all post references. Category deletion is restricted while referenced. Publishing and new active-category assignment checks remain application-service responsibilities in later phases.
- The existing `categories.slug` unique constraint supports server-generated slugs; this decision needs no schema change. Dashboard counts are query results and need no persisted aggregate or schema change.
- The initial migration has a guarded down operation. It drops all four tables and permanently deletes their data; require a backup and a disposable database before invoking it.
- The second migration adds only the transient login limiter table. Its guarded rollback drops that table and its ephemeral counters; it does not alter the CMS entity schema.
- The third migration adds `users.auth_version` for server-side session revocation after credential rotation/reset. Its guarded rollback drops the column and therefore removes revocation state; coordinate rollback with code deployment and invalidate sessions. All three migrations still require verification against Oracle MySQL 8.0.16 or newer; MariaDB is not an accepted substitute.

The migration runner uses `DB_*` settings by default. Deployments should provide a separate, short-lived migration account with `MIGRATION_DB_*` overrides; the application runtime account should not have DDL or `DROP` privileges. Production database connections require a trusted `DB_SSL_CA` certificate and PDO server-certificate verification; remote database hosts require the CA in all environments. Loopback development may omit TLS. Configure MySQL `require_secure_transport=ON` for production so the server also rejects plaintext connections.

## 10. Data lifecycle and privacy

- Collect only account data required for authentication/operation.
- Avoid collecting email unless the feature needs it.
- Keep audit metadata minimal.
- Establish retention policies before production deployment.
- Ensure summaries can be regenerated when their source changes; mark stale data rather than falsely presenting it as current.
- Summary generation runs only after backend authorization. The provider adapter receives bounded article text and fixed instructions; it gets no MySQL credentials or direct application privileges. The backend stores validated results with the normal application data layer.
- View tracking, tags, featured-image uploads, public author profiles, remember-me, password recovery, and trash/restore have no Version 1.0 tables or columns and are deferred.
